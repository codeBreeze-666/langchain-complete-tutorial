# 第四章：工具篇

> 工具（Tool）是 Agent 的手和脚。大模型本身只能"思考"，通过工具才能"行动"。本章从工具基础（@tool 装饰器）、高级特性（StructuredTool、输入验证、错误处理、工具链）到工具注入（InjectedState、InjectedStore、配置注入、上下文感知），逐步深入讲解 LangChain 工具体系。

---

## 4.1 工具基础（tool_basics.py）

### 知识点

| 概念 | 作用 |
|------|------|
| **@tool 装饰器** | 将 Python 函数转换为 LangChain 工具 |
| **Agent 使用工具** | Agent 自动选择和调用合适的工具 |
| **多工具协作** | Agent 组合使用多个工具完成复杂任务 |

本项目定义了 5 个原创工具：

| 工具名 | 功能 | 参数 |
|--------|------|------|
| `get_current_time` | 获取当前时间 | timezone（时区） |
| `calculate` | 执行数学计算 | expression（数学表达式） |
| `generate_random_number` | 生成随机数 | min_val, max_val |
| `word_count` | 统计文本字数 | text（文本） |
| `convert_temperature` | 温度单位转换 | value, from_unit, to_unit |

### 运行方式

```bash
python src/chains/tool_basics.py
```

运行后进入交互式菜单，选择 1-3 运行不同示例。

### 示例详解

#### 示例1：单个工具使用

**场景**：直接调用 5 个工具，测试每个工具的功能。

**核心代码**：

```python
from langchain_core.tools import tool

@tool
def get_current_time(timezone: str = "Asia/Shanghai") -> str:
    """获取当前时间

    Args:
        timezone: 时区（默认：Asia/Shanghai）

    Returns:
        当前时间的字符串
    """
    from datetime import datetime
    import pytz
    try:
        tz = pytz.timezone(timezone)
        current_time = datetime.now(tz)
        return f"当前时间（{timezone}）：{current_time.strftime('%Y-%m-%d %H:%M:%S')}"
    except Exception as e:
        return f"获取时间失败：{str(e)}"

# 直接调用工具
result = tool_func.invoke({"timezone": "Asia/Shanghai"})
```

**5 个工具详解**：

| 工具 | 实现要点 |
|------|----------|
| `get_current_time` | 使用 `pytz` 处理时区，`try-except` 捕获异常 |
| `calculate` | 安全计算：白名单字符校验 `allowed_chars`，仅允许数字和基本运算符 |
| `generate_random_number` | 使用 `random.randint()`，支持自定义范围 |
| `word_count` | 分别统计中文字符（Unicode 范围）和英文单词 |
| `convert_temperature` | 先转摄氏度再转目标单位，支持 C/F/K 三种单位 |

**实战要点**：
- `@tool` 装饰器将函数转换为工具，Docstring 定义工具的描述和参数
- 工具的 Docstring 非常重要，Agent 根据它判断何时调用该工具
- `tool.invoke()` 可直接调用工具，无需经过 Agent
- 工具内部应做好异常处理，返回友好的错误信息

#### 示例2：Agent 使用工具

**场景**：用自然语言提问，Agent 自动理解意图并选择合适的工具。

**核心代码**：

3. Agent 构造工具调用参数，执行工具
4. Agent 根据工具返回结果，组织最终回答

**实战要点**：
- `create_agent()` 创建 Agent（LangChain v1 推荐方式）
- `system_prompt` 参数定义 Agent 的行为风格
- Agent 自动管理执行循环（思考→行动→观察→回答）
- Agent 通过工具的 docstring 理解工具用途

### 示例详解

#### 示例1：StructuredTool - 结构化工具

**场景**：邮件发送工具——使用 StructuredTool 定义，Pydantic 模型验证邮箱格式。

**核心代码**：

```python
from langchain_core.tools import StructuredTool
from pydantic import BaseModel, Field, field_validator
import re

class EmailInput(BaseModel):
    """邮件输入验证模型"""
    recipient: str = Field(description="收件人邮箱")
    subject: str = Field(description="邮件主题")
    content: str = Field(description="邮件内容")

    @field_validator('recipient')
    @classmethod
    def validate_email(cls, v):
        """验证邮箱格式"""
        if not re.match(r'^[\w\.-]+@[\w\.-]+\.\w+$', v):
            raise ValueError('邮箱格式不正确')
        return v

def send_email(recipient: str, subject: str, content: str) -> str:
    """发送邮件（模拟）"""
    return f"✅ 邮件已发送\n收件人：{recipient}\n主题：{subject}\n内容：{content[:50]}..."

# 使用 StructuredTool 创建工具
email_tool = StructuredTool(
    name="send_email",
    description="发送邮件给指定收件人",
    func=send_email,
    args_schema=EmailInput
)

# 调用（会自动验证邮箱格式）
result = email_tool.invoke({"recipient": "test@example.com", "subject": "测试", "content": "内容"})
```

**运行流程**：
1. 定义 `EmailInput` Pydantic 模型，包含 `field_validator` 验证邮箱格式
2. `StructuredTool` 将函数和验证模型绑定
3. 调用 `invoke()` 时，Pydantic 自动验证参数
4. 验证失败抛出异常，验证通过则执行函数

**实战要点**：
- `StructuredTool` 比 `@tool` 更灵活，支持自定义参数验证
- `args_schema=EmailInput` 指定参数验证模型
- `field_validator` 自定义验证规则（如邮箱格式、手机号格式等）
- 验证失败时 Agent 会收到错误信息，可以重试或调整参数

#### 示例2：输入验证 - 多种验证规则

**场景**：用户注册工具——使用 Pydantic 的多种内置验证器（长度、范围、正则）。

**核心代码**：

```python
class UserProfile(BaseModel):
    """用户资料模型"""
    username: str = Field(description="用户名", min_length=3, max_length=20)
    age: int = Field(description="年龄", ge=0, le=150)
    email: str = Field(description="邮箱")
    phone: str = Field(description="手机号", pattern=r'^1[3-9]\d{9}$')

    @field_validator('username')
    @classmethod
    def validate_username(cls, v):
        if not v.isalnum():
            raise ValueError('用户名只能包含字母和数字')
        return v

    @field_validator('email')
    @classmethod
    def validate_email(cls, v):
        if not re.match(r'^[\w\.-]+@[\w\.-]+\.\w+$', v):
            raise ValueError('邮箱格式不正确')
        return v

@tool(args_schema=UserProfile)
def register_user(username: str, age: int, email: str, phone: str) -> str:
    """注册用户"""
    return f"✅ 用户注册成功\n用户名：{username}\n年龄：{age}\n邮箱：{email}\n手机：{phone}"
```

**Pydantic 验证器一览**：

| 验证方式 | 示例 | 说明 |
|----------|------|------|
| `min_length` / `max_length` | `min_length=3, max_length=20` | 字符串长度限制 |
| `ge` / `le` | `ge=0, le=150` | 数值范围限制（≥ / ≤） |
| `pattern` | `pattern=r'^1[3-9]\d{9}$'` | 正则表达式验证 |
| `field_validator` | `@field_validator('username')` | 自定义验证逻辑 |

**实战要点**：
- `@tool(args_schema=UserProfile)` 也可以指定参数验证模型
- Pydantic 提供多种内置验证器，覆盖大部分场景
- `field_validator` 用于自定义验证逻辑，优先级高于内置验证器
- 验证失败时 Agent 会收到具体错误信息，可以纠正后重试

#### 示例3：错误处理 - 友好的错误提示

**场景**：除法计算和文件读取工具——展示工具内部的异常处理机制。

**核心代码**：

```python
@tool
def divide_numbers(a: float, b: float) -> str:
    """除法计算"""
    try:
        if b == 0:
            return "❌ 错误：除数不能为零"
        result = a / b
        return f"计算结果：{a} ÷ {b} = {result}"
    except Exception as e:
        return f"❌ 计算失败：{str(e)}"

@tool
def read_file(file_path: str) -> str:
    """读取文件内容"""
    try:
        if not os.path.exists(file_path):
            return f"❌ 错误：文件不存在 - {file_path}"
        with open(file_path, 'r', encoding='utf-8') as f:
            content = f.read()
            return f"文件内容（前100字符）：\n{content[:100]}..."
    except PermissionError:
        return f"❌ 错误：没有权限读取文件 - {file_path}"
    except Exception as e:
        return f"❌ 读取失败：{str(e)}"
```

**错误处理策略**：

| 错误类型 | 处理方式 | 示例 |
|----------|----------|------|
| 业务逻辑错误 | 返回友好提示 | 除数为零 → "除数不能为零" |
| 文件不存在 | 先检查再读取 | `os.path.exists()` |
| 权限不足 | 捕获 `PermissionError` | "没有权限读取文件" |
| 未知异常 | 通用 `try-except` | "操作失败：{错误信息}" |

**实战要点**：
- 工具内部必须处理可能的异常，避免崩溃影响 Agent
- 返回用户友好的错误提示，而非原始异常堆栈
- Agent 可以根据错误信息调整策略（如换个参数重试）
- 检查前置条件（如文件是否存在、参数是否合法）比异常捕获更优雅

#### 示例4：工具链 - 多个工具组合

**场景**：活动规划助手——先查询天气，再根据天气推荐活动。

**核心代码**：

```python
@tool
def get_weather(city: str) -> str:
    """获取天气（模拟）"""
    weather_data = {
        "北京": "晴天 18°C",
        "上海": "多云 22°C",
        "广州": "小雨 25°C"
    }
    return weather_data.get(city, f"未找到{city}的天气信息")

@tool
def get_activity_recommendation(weather: str) -> str:
    """根据天气推荐活动"""
    if "晴" in weather:
        return "推荐活动：户外跑步、野餐、骑行"
    elif "云" in weather:
        return "推荐活动：散步、逛商场、看电影"
    elif "雨" in weather:
        return "推荐活动：室内运动、看书、烹饪"
    else:
        return "推荐活动：根据实际情况安排"

# Agent 自动组合使用两个工具
tools = [get_weather, get_activity_recommendation]
agent = create_agent(model, tools, system_prompt="你是一个智能助手...")

result = agent.invoke({"messages": [("user", "北京今天适合做什么？")]})
# Agent 先调用 get_weather("北京") → "晴天 18°C"
# 再调用 get_activity_recommendation("晴天 18°C") → "户外跑步、野餐、骑行"
```

**运行流程**：
1. 用户输入"北京今天适合做什么？"
2. Agent 判断需要先查天气，调用 `get_weather("北京")`
3. 获取天气结果"晴天 18°C"
4. Agent 将天气结果作为参数，调用 `get_activity_recommendation("晴天 18°C")`
5. 获取活动推荐，组织最终回答

**实战要点**：
- Agent 自动决定工具调用顺序，无需手动编排
- 前一个工具的输出可以作为后一个工具的输入（工具链）
- 工具链适合复杂的多步骤任务（查询→分析→推荐）
- `verbose=True` 可以清晰看到 Agent 的工具调用链

#### 示例1：InjectedState - 注入状态

**场景**：状态感知查询——工具根据对话历史和步骤数调整响应策略。

```python
        self.conversation_history.append({
```

#### 示例2：InjectedStore - 注入存储

**场景**：共享存储操作——多个工具通过共享存储传递数据。

**核心代码**：

```python
class SimulatedStore:
    """模拟共享存储"""
    def __init__(self):
        self._data = {}

    def set(self, key: str, value):
        self._data[key] = {
            "value": value,
            "updated_at": datetime.now().isoformat()
        }

    def get(self, key: str, default=None):
        entry = self._data.get(key)
        return entry["value"] if entry else default

    def delete(self, key: str) -> bool:
        if key in self._data:
            del self._data[key]
            return True
        return False

    def list_keys(self) -> list:
        return list(self._data.keys())
```

**交互命令**：
- `set <键> <值>` — 存储数据
- `get <键>` — 读取数据
- `delete <键>` — 删除数据
- `list` — 列出所有数据

**运行流程**：
1. 初始化 `SimulatedStore`，预设一些初始数据（用户偏好、会话信息）
2. 用户通过命令操作存储
3. 工具通过注入的存储引用读写数据
4. 多个工具可共享同一存储实例

**实战要点**：
- `InjectedStore` 提供跨工具的共享存储空间
- 工具通过注入获取存储引用，无需参数传递
- 适合需要工具间数据传递和持久化的场景
- LangChain 中 Store 通过 `RunnableConfig` 注入

#### 示例3：配置注入 - Config Injection

**场景**：配置感知问候——工具根据运行时配置（语言、地区、温度参数）动态调整行为。

**核心代码**：

```python
class SimulatedConfig:

    def __init__(self):

            "model": "glm-4.7-flash",

            "region": "cn",

def _config_aware_greet(name: str, config: SimulatedConfig) -> str:
    lang = config.get("language", "zh-CN")
```

**交互命令**：

2. 用户通过 `greet` 命令触发问候，工具根据配置生成不同语言和语气的问候
3. 修改配置后，同一工具的行为随之改变
4. `preset` 命令一键切换预设配置

**实战要点**：
- 配置注入让同一工具在不同配置下行为不同
- `RunnableConfig` 是 LangChain 配置传递的标准方式
- 适合多语言、多环境、多租户等场景
- 工具通过 `config` 参数接收注入的配置

#### 示例4：上下文感知工具 - Context-Aware Tool

**场景**：上下文感知搜索——综合利用 State/Store/Config 三种注入，根据上下文动态调整输出。

**核心代码**：

```python
def _context_aware_search(query: str, state: SimulatedAgentState,
                          store: SimulatedStore, config: SimulatedConfig) -> str:
    # 从配置获取语言偏好
    lang = config.get("language", "zh-CN")

    # 从存储获取用户偏好
    user_theme = store.get("用户偏好.主题", "默认")
    user_lang_pref = store.get("用户偏好.语言", "未设置")

    # 根据对话历史判断上下文深度
    history_count = len(state.conversation_history)
    if history_count <= 2:
        depth = "浅层"
        detail_level = "详细解释"
    elif history_count <= 6:
        depth = "中层"
        detail_level = "适度精简"
    else:
        depth = "深层"
        detail_level = "高度概括"

    # 根据语言返回不同搜索结果
    # 根据上下文深度调整输出详略
    # 将搜索历史记录到存储
    store.set(f"搜索历史.步骤{state.current_step}", query)
```

**交互命令**：
- `search <查询>` — 执行上下文感知搜索
- `set-store <键> <值>` — 修改用户偏好（存储）
- `set-config <键> <值>` — 修改运行时配置
- `info` — 查看当前上下文信息
- `debug on/off` — 开关调试模式

**运行流程**：
1. 同时初始化 `SimulatedAgentState`、`SimulatedStore`、`SimulatedConfig`
2. 搜索时，工具自动读取三种注入的上下文
3. 根据对话深度调整输出详略（浅层→详细，深层→概括）
4. 根据语言配置返回不同语言的搜索结果
5. 搜索历史自动记录到存储中

**实战要点**：
- 上下文感知工具综合运用多种注入机制
- 工具可根据对话深度自动调整输出详略
- 用户偏好和配置影响工具行为
- 这是构建智能 Agent 工具的核心设计模式

## 本章小结

| 章节 | 核心技术 | 关键 API |
|------|----------|----------|
| 4.1 工具基础 | @tool 装饰器 / Agent 使用工具 / 多工具协作 | `@tool` / `create_agent()` / `system_prompt` |
| 4.2 工具高级特性 | StructuredTool / field_validator / 错误处理 / 工具链 | `StructuredTool(args_schema=...)` / `@field_validator` / `try-except` |
| 4.3 工具注入 | InjectedState / InjectedStore / 配置注入 / 上下文感知 | `Annotated[type, InjectedToolArg]` / `RunnableConfig` |

**核心认知**：
1. **工具是 Agent 的能力边界**——没有工具的 Agent 只能"思考"，有了工具才能"行动"
2. **@tool 是最简单的工具定义方式**——一个装饰器 + Docstring 就能创建工具，适合快速原型
3. **StructuredTool 适合复杂参数验证**——当需要邮箱校验、手机号校验等时，使用 Pydantic 模型
4. **错误处理是工具的底线**——工具内部必须 try-except，返回友好错误信息，避免崩溃影响 Agent
5. **工具链让 Agent 具备复杂推理能力**——Agent 自动编排工具调用顺序，前一个工具的输出作为后一个的输入
6. **注入是工具的"第六感"**——InjectedState/Store/Config 让工具感知运行上下文，无需显式传参
7. **上下文感知是工具的终极形态**——综合运用多种注入，工具根据对话深度、用户偏好、配置动态调整行为
