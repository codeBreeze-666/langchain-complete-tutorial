# 第六章：中间件篇

## 6.1 中间件基础（middleware_basics.py）

### 知识点：BaseCallbackHandler、日志中间件、Token追踪、性能监控、自定义回调

**运行方式：**

```bash
python src/chains/middleware_basics.py
```

**核心概念：**

- **BaseCallbackHandler**：LangChain 的回调基类，所有中间件的父类
- **on_llm_start / on_llm_end**：模型调用前后的钩子函数
- **中间件模式**：在不修改业务逻辑的前提下添加横切功能（日志、监控等）
- **callbacks 参数**：通过 `config={"callbacks": [...]}` 注入中间件

**中间件注入方式：**

```python
# 创建中间件实例
logging_middleware = LoggingMiddleware()

# 通过 config 参数注入，无需修改业务代码
response = chain.invoke(
    {"question": question},
    config={"callbacks": [logging_middleware]}
)
```

### 示例1：日志中间件 — 记录每次调用的输入输出

**功能说明：** 继承 `BaseCallbackHandler`，在 `on_llm_start` 捕获输入，在 `on_llm_end` 捕获输出，实现完整的调用日志记录。

**关键代码：**

```python
from langchain_core.callbacks import BaseCallbackHandler

class LoggingMiddleware(BaseCallbackHandler):
    def __init__(self):
        self.call_logs = []
        self._current_prompts = []

    def on_llm_start(self, serialized, prompts, **kwargs):
        """LLM 调用开始时记录输入"""
        self._current_prompts = prompts
        print(f"[日志中间件] 开始调用 - 输入: {prompts[0][:80]}")

    def on_llm_end(self, response, **kwargs):
        """LLM 调用结束时记录输出"""
        output_text = response.generations[0][0].text
        self.call_logs.append({"input": self._current_prompts[0], "output": output_text})
        print(f"[日志中间件] 调用完成 - 输出: {output_text[:80]}")

    def on_llm_error(self, error, **kwargs):
        """LLM 调用出错时记录"""
        print(f"[日志中间件] 调用出错 - 错误: {error}")
```

**实战要点：**

1. `BaseCallbackHandler` 是所有中间件的基类，继承并重写钩子方法即可
2. `on_llm_start` 捕获输入（prompts 参数），`on_llm_end` 捕获输出（response 参数）
3. 通过 `config={"callbacks": [...]}` 注入中间件，**无需修改业务代码**
4. `on_llm_error` 处理调用异常，保证日志完整性

### 示例2：Token追踪中间件 — 统计每次调用的Token使用量

**功能说明：** 从 `response.llm_output["token_usage"]` 中提取 Token 用量，统计输入/输出/总 Token 消耗。

**关键代码：**

```python
class TokenTrackerMiddleware(BaseCallbackHandler):
    def __init__(self):
        self.total_tokens = 0
        self.prompt_tokens = 0
        self.completion_tokens = 0
        self.call_records = []

    def on_llm_end(self, response, **kwargs):
        """LLM 调用结束时统计 Token"""
        if response.llm_output and "token_usage" in response.llm_output:
            usage = response.llm_output["token_usage"]
            self.total_tokens += usage.get("total_tokens", 0)
            self.prompt_tokens += usage.get("prompt_tokens", 0)
            self.completion_tokens += usage.get("completion_tokens", 0)
            print(f"[Token追踪] 本次: 总{usage['total_tokens']} (输入{usage['prompt_tokens']} + 输出{usage['completion_tokens']})")
```

**实战要点：**

1. `token_usage` 在 `llm_output` 中返回（**部分模型可能不返回**）
2. 追踪 Token 消耗对**成本管理**至关重要
3. 可按需求扩展为按用户、按功能维度的 Token 统计
4. 累计统计可用于设置预算阈值和告警

### 示例3：性能监控中间件 — 记录每次调用的耗时

**功能说明：** 在 `on_llm_start` 记录开始时间，在 `on_llm_end` 计算耗时，使用 `run_id` 关联同一次调用。

**关键代码：**

```python
class PerformanceMonitorMiddleware(BaseCallbackHandler):
    def __init__(self):
        self._start_times = {}
        self.call_metrics = []

    def on_llm_start(self, serialized, prompts, **kwargs):
        """记录调用开始时间"""
        run_id = str(kwargs.get("run_id", id(prompts)))
        self._start_times[run_id] = time.time()
        print("[性能监控] 调用开始...")

    def on_llm_end(self, response, **kwargs):
        """记录调用结束时间并计算耗时"""
        run_id = str(kwargs.get("run_id", "unknown"))
        start_time = self._start_times.pop(run_id, None)
        if start_time:
            elapsed = time.time() - start_time
            self.call_metrics.append({"elapsed_seconds": round(elapsed, 3)})
            print(f"[性能监控] 调用完成 - 耗时: {elapsed:.3f}秒")
```

**实战要点：**

1. `run_id` 用于关联同一次调用的开始和结束事件
2. 性能数据帮助识别慢查询和优化方向
3. 可扩展为设置耗时阈值、超时告警等功能
4. 平均/最快/最慢耗时统计有助于选择合适的模型

### 示例4：自定义回调中间件 — 策略模式实现灵活回调

**功能说明：** 通过构造函数注入自定义处理函数（on_start/on_end/on_error），实现策略模式，灵活切换不同的回调行为。

**关键代码：**

```python
class CustomCallbackMiddleware(BaseCallbackHandler):
    def __init__(self, on_start=None, on_end=None, on_error=None):
        self.on_start = on_start
        self.on_end = on_end
        self.on_error = on_error

    def on_llm_start(self, serialized, prompts, **kwargs):
        if self.on_start:
            self.on_start(prompts)

    def on_llm_end(self, response, **kwargs):
        if self.on_end:
            output_text = response.generations[0][0].text
            self.on_end(self._current_prompts, output_text)

# 注入不同的策略
custom_callback = CustomCallbackMiddleware(
    on_start=lambda prompts: print(f"收到输入: {prompts[0][:60]}"),
    on_end=lambda inp, out: print(f"输入 {len(inp[0])} 字符 -> 输出 {len(out)} 字符"),
    on_error=lambda err: print(f"发生错误: {err}"),
)
```

**实战要点：**

1. 通过构造函数注入处理函数，**策略模式**让回调逻辑可动态切换
2. 不同场景可注入不同的 on_start / on_end / on_error
3. 无需修改中间件代码即可改变监控行为
4. 适合需要动态改变监控逻辑的场景

## 6.2 错误处理（error_handling.py）

### 知识点：错误重试(指数退避)、模型降级(with_fallbacks)、输出验证、优雅降级

**运行方式：**

```bash
python src/chains/error_handling.py
```

**核心概念：**

| 策略 | 核心机制 | 解决的问题 |
|------|---------|-----------|
| 错误重试 | 指数退避自动重试 | 网络波动、API 限流 |
| 模型降级 | with_fallbacks 切换备用模型 | 主模型不可用 |
| 输出验证 | PydanticOutputParser + 自定义校验 | 输出格式不稳定 |
| 优雅降级 | 三级降级保障 | 服务整体可用性 |

---

### 示例1：错误重试 — 指数退避自动重试

**功能说明：** 当 API 调用失败时自动重试，重试间隔按指数增长（1s → 2s → 4s），最多重试 3 次。

**关键代码：**

```python
def retry_chain_invoke(chain, inputs, max_retries=3, base_delay=1):
    """带指数退避重试机制的链调用"""
    for attempt in range(1, max_retries + 1):
        try:
            result = chain.invoke(inputs)
            if attempt > 1:
                print(f"✅ 第 {attempt} 次重试成功！")
            return result
        except Exception as e:
            print(f"❌ 第 {attempt} 次调用失败: {type(e).__name__}")
            if attempt < max_retries:
                delay = base_delay * (2 ** (attempt - 1))  # 指数退避
                print(f"⏳ 等待 {delay} 秒后重试...")
                time.sleep(delay)
            else:
                print(f"🚫 已达最大重试次数 ({max_retries})")
                return None
```

**实战要点：**

1. **指数退避（Exponential Backoff）** 是最常用的重试策略
2. 重试次数不宜过多，一般 **3-5 次** 即可
3. 每次重试间隔翻倍，避免短时间内大量请求冲击服务端
4. 对**瞬时错误**（网络超时、限流）重试，对**逻辑错误**不重试

### 示例2：模型降级 — with_fallbacks 切换备用模型

**功能说明：** 主模型失败时自动切换到备用模型，保证服务可用性。演示 LangChain 内置 `.with_fallbacks()` 和手动降级两种方式。

**关键代码：**

```python
# 方式一：LangChain 内置降级
chain_with_fallback = primary_chain.with_fallbacks([fallback_chain])
result = chain_with_fallback.invoke({"user_input": user_input})

# 方式二：手动降级（更灵活的控制）
def invoke_with_fallback(primary, fallbacks, inputs):
    try:
        result = primary.invoke(inputs)
        return result, "主模型"
    except Exception as e:
        print(f"❌ 主模型失败: {e}")

    for i, fallback in enumerate(fallbacks, 1):
        try:
            result = fallback.invoke(inputs)
            return result, f"备用模型 #{i}"
        except Exception as e:
            print(f"❌ 备用模型 #{i} 失败: {e}")

    return None, None
```

**实战要点：**

1. `.with_fallbacks()` 是 LangChain **原生降级方案**，简洁优雅
2. 可配置多个备用模型，按顺序尝试
3. 手动降级可以添加更细粒度的控制（如日志、告警）
4. 生产建议：主模型 + 同厂商轻量模型 + **异厂商模型**（避免同厂商全线故障）

### 示例3：输出验证 — PydanticOutputParser + 自定义校验

**功能说明：** 验证模型输出是否符合预期格式，包含两种验证方式：PydanticOutputParser 强制结构化输出、自定义验证逻辑检查业务规则。

**方式一：PydanticOutputParser 结构化输出**

```python
from pydantic import BaseModel, Field
from langchain_core.output_parsers import PydanticOutputParser

class ProductInfo(BaseModel):
    name: str = Field(description="产品名称")
    category: str = Field(description="产品类别")
    price: float = Field(description="价格（元）")
    description: str = Field(description="简要描述")

pydantic_parser = PydanticOutputParser(pydantic_object=ProductInfo)
chain = structured_prompt | model | pydantic_parser

try:
    result = chain.invoke({"product_desc": product_desc, "format_instructions": ...})
except Exception as e:
    # 解析失败时降级为纯文本
    text_chain = text_prompt | model | StrOutputParser()
    text_result = text_chain.invoke({"product_desc": product_desc})
```

**方式二：自定义验证逻辑**

```python
# 解析 JSON 后进行业务规则校验
parsed = json.loads(raw_output)

errors = []
if "answer" not in parsed or not parsed["answer"]:
    errors.append("缺少 answer 字段或为空")
if "confidence" in parsed:
    conf = parsed["confidence"]
    if not isinstance(conf, (int, float)) or conf < 0 or conf > 1:
        errors.append(f"confidence 值无效: {conf}（应在 0-1 之间）")
```

**实战要点：**

1. `PydanticOutputParser` 强制输出为指定结构，解析失败抛异常
2. 解析失败时降级为 `StrOutputParser` 获取纯文本
3. 自定义验证可以检查业务规则（如置信度范围 0-1）
4. JSON 输出需要清理 markdown 代码块标记（` ```json ` ）

### 示例4：优雅降级 — 三级降级保障

**功能说明：** 出错时逐级降级，保证服务不崩溃。三级保障：正常调用 → 简化 prompt 重试 → 兜底模板。

**降级流程：**

```
用户输入 → 第一级：正常调用
  ├─ 成功 → 返回结果（状态：🟢 正常）
  └─ 失败 → 第二级：简化 prompt 重试
      ├─ 成功 → 返回结果（状态：🟡 降级）
      └─ 失败 → 第三级：使用预设兜底模板
          └─ 返回友好提示（状态：🔴 兜底）
```

**关键代码：**

```python
FALLBACK_TEMPLATES = {
    "翻译": "抱歉，翻译服务暂时不可用，请稍后重试。",
    "总结": "抱歉，总结服务暂时不可用，原始内容如下：\n{content}",
    "问答": "抱歉，AI 问答服务暂时不可用，请联系管理员。",
    "默认": "抱歉，服务暂时不可用，请稍后再试。",
}

def graceful_invoke(chain, inputs, service_name="默认", context=None):
    # 第一级：正常调用
    try:
        result = chain.invoke(inputs)
        if result: return result, "success"
    except Exception: pass

    # 第二级：简化 prompt 重试
    try:
        simple_chain = simplified_prompt | model | StrOutputParser()
        result = simple_chain.invoke({"user_input": inputs.get("user_input", "")})
        if result: return result, "degraded"
    except Exception: pass

    # 第三级：兜底模板
    template = FALLBACK_TEMPLATES.get(service_name, FALLBACK_TEMPLATES["默认"])
    return template, "fallback"
```

**实战要点：**

1. 三级降级：正常 → 简化重试 → 兜底模板，层层保障
2. 每级降级都要**记录日志**，便于事后排查
3. 兜底模板要**友好**，不能暴露技术细节（如堆栈信息）
4. 降级策略根据业务优先级灵活调整

## 本章小结

本章涵盖了 LangChain 中间件和错误处理两大主题：

1. **中间件基础**：掌握了 `BaseCallbackHandler` 的使用，学会通过 `on_llm_start` / `on_llm_end` / `on_llm_error` 钩子实现日志记录、Token 追踪、性能监控和自定义回调。核心原则是通过 `callbacks` 参数注入中间件，**不修改业务代码**。

2. **错误处理**：学习了四种保障服务可靠性的策略——指数退避重试（应对瞬时错误）、模型降级（应对主模型故障）、输出验证（应对格式不稳定）、优雅降级（保证服务不崩溃）。

**关键原则：**
- 中间件是横切关注点的优雅解决方案，日志/监控/统计等不应侵入业务代码
- 错误处理要分层次：重试解决瞬时问题，降级解决持续故障
- 优雅降级是生产环境的底线——即使 AI 完全不可用，系统也要给出友好响应
- 每次降级和错误都要记录日志，为问题排查和系统优化提供数据
